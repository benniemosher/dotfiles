# Shared MCP registry

One canonical list of MCP (Model Context Protocol) servers, rendered into every AI
tool's native config. Define a server once in [`servers.yaml`](servers.yaml); Kiro,
Claude Code, and Codex all get it on the next `chezmoi apply`.

## Why

Each AI tool wants its MCP servers in a different file and, for Codex, a different
format. Maintaining the same server list by hand in three places drifts immediately.
Instead, `servers.yaml` is the single source of truth and chezmoi templates render it
per tool.

```
ai/mcp/servers.yaml                    canonical source (plain YAML, you edit this)
        │
        │  rendered by chezmoi templates
        ▼
  ┌─────────────────────────┬──────────────────────────────┬────────────────────────┐
  │ Kiro CLI                │ Claude Code (CLI)            │ Codex (prepped)        │
  │ ~/.kiro/settings/       │ registered via               │ ~/.codex/config.toml   │
  │   mcp.json              │   `claude mcp add-json`      │                        │
  │                         │   (user scope, ~/.claude.json)│                       │
  └─────────────────────────┴──────────────────────────────┴────────────────────────┘
```

`ai/` deploys to `~/ai`, and `~/.config/ai` symlinks to it, so the registry is also
readable at `~/.config/ai/mcp/servers.yaml` on every machine.

## Rendering

Shared logic lives in chezmoi template partials:

- `.chezmoitemplates/mcp-servers-json` — emits the `mcpServers` object for JSON clients
  (Kiro).
- `.chezmoitemplates/mcp-servers-claude-code-sh` — emits `claude mcp add-json` commands
  for Claude Code (CLI).
- `.chezmoitemplates/mcp-servers-toml` — emits `[mcp_servers.NAME]` tables for Codex.

Per-tool wiring:

| Tool | Rendered by | Notes |
|------|-------------|-------|
| Kiro CLI | `run_onchange_setup-ai-config.sh.tmpl` | `.kiro/settings` is chezmoiignored (Kiro rewrites it), so the config is generated by the run_onchange script, not a tracked template. Gated on `use_kiro`. |
| Claude Code (CLI) | `run_onchange_setup-ai-config.sh.tmpl` | Claude Code keeps user MCP servers in `~/.claude.json`, a large stateful file we must not own. The script runs `claude mcp add-json ... --scope user` per server (remove-then-add, idempotent). Runs whenever `claude` is on PATH. |
| Codex | `dot_codex/config.toml.tmpl` | Inactive until a machine sets `use_codex = true`; `.codex` is otherwise chezmoiignored. |

### stdio-only clients

Claude Code (at user scope here) and Codex launch **stdio** servers; a raw `url`/`type: http`
entry isn't used. The renderers bridge remote (http) servers through
`npx -y mcp-remote <url>` for those clients. Kiro supports http natively, so it gets the
`url` form directly.

## Runtimes

| Runtime | Provided by | Used for |
|---------|-------------|----------|
| `uvx` (via `uv`) | mise (`dot_config/mise/config.toml.tmpl`) | AWS Labs servers (`uvx awslabs.*-mcp-server`) |
| `docker` | installed per platform | Terraform MCP server image |
| `npx` (via node) | mise | `mcp-remote` bridge for stdio-only clients |

AWS Labs servers authenticate with ambient AWS credentials. `AWS_PROFILE` is deliberately
left unset in the registry so each machine/session uses its own default profile or whatever
is exported; set it per server if you need a fixed profile.

## Registry schema

Each entry under `servers:`:

| Field | Values | Meaning |
|-------|--------|---------|
| `transport` | `stdio` \| `http` | How the client reaches the server. |
| `runtime` | `uvx` \| `docker` \| `remote` | `stdio` uses uvx/docker; `http` uses remote. |
| `package` | string | uvx package spec (runtime `uvx`). |
| `image` | string | docker image ref (runtime `docker`). |
| `url` | string | endpoint (transport `http`). |
| `args` | list | extra argv appended after the package/image. |
| `env` | map | environment variables (stdio only). |
| `autoApprove` | list | tool-name globs a client may run without prompting. |
| `enabled` | bool | `false` parks a server in the registry without deploying it. |
| `tools` | list | which clients get it (`kiro`, `claude`, `codex`); omit = all. |

## How to add a server

1. Add an entry to [`servers.yaml`](servers.yaml). Pick the runtime: `uvx` for a Python
   package, `docker` for an image, `remote` for an http endpoint.
2. `chezmoi apply`.
3. Restart the AI tool so it reloads its MCP config.

Example (uvx):

```yaml
  s3-tables:
    transport: stdio
    runtime: uvx
    package: "awslabs.s3-tables-mcp-server@latest"
    env:
      FASTMCP_LOG_LEVEL: "ERROR"
    autoApprove: []
```

To limit a server to one tool, add `tools: [kiro]`. To park one without deploying it, add
`enabled: false`.

## Scope

These are general-purpose servers (IaC, AWS, databases) used on every machine, work and
personal. They carry no secrets — auth is ambient AWS credentials or public endpoints — so
the registry is safe to commit. Tool-specific or credentialed servers (e.g. a project's
Jira/GitLab MCP with a token) stay in that project's own `.kiro/settings/mcp.json` or the
tool's connector UI, not here.
